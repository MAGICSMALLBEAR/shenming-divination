# 實機品質驗收與效能量測協定

本文件是「神明占卜」在發佈前的真機驗收清單與可回填紀錄。它補足單元測試、型別檢查、lint 與 Web 匯出無法驗證的觸控、原生權限、動畫流暢度、記憶體與中斷恢復行為。

> 不要以模擬器或單次目視結果取代本協定。每一筆量測都要註明裝置、作業系統、App 版本與 commit SHA；沒有數字或螢幕錄影的「正常」不算完成。

## 1. 進入條件與版本識別

先在待測 commit 執行：

```powershell
npm.cmd test -- --runInBand
npx.cmd tsc --noEmit
npm.cmd run lint
npm.cmd run export:web
git rev-parse --short HEAD
```

本輪基準版本：`67a28e0`（神明肖像載入失敗替代卡）。若改用後續 commit，請在紀錄表取代 SHA，且重新跑一次上述檢查。

候選發佈 build 請用 `npm.cmd run release:rc` 產生 `docs/releases/` 下的候選紀錄：它會在乾淨的 commit 上跑完上述檢查，並記錄測試 SHA、變更摘要與本協定的 A/I/T/W 紀錄連結。安裝後在「設定 → 關於」底部核對版本與 build 號。W 裝置測試前，先在本機跑 `npm.cmd run test:e2e:pwa`（需全域 Playwright）確認離線、更新與快取失效流程；部署後再跑 `npm.cmd run test:e2e:pwa -- --url https://shenming-divination.vercel.app` 對正式站驗證（新版本提示情境需可替換 sw.js，正式站會略過）。

真機應優先使用 development build 或候選發佈 build；Expo Go 只可用於快速介面巡檢，不能作為原生權限、通知、音訊、效能或上架驗收的唯一證據。Expo 的 development build 可透過 `npx expo run:android --device` 或 macOS 上的 `npx expo run:ios --device` 安裝；僅在原生相依套件或 `app.json` 變更後才需要重建。iOS 16 以上測試機需先開啟 Developer Mode。

首次製作 development build 前，確認團隊同意新增 `expo-dev-client` 與原生建置檔；這會改變專案依賴與建置輸出，不是本 QA 協定自動執行的步驟。

## 2. 最小裝置矩陣

| 代號 | 必要裝置 | 記錄欄位 | 主要風險 |
| --- | --- | --- | --- |
| A | 低階 Android 實機（60 Hz、約 3–4 GB RAM） | 品牌/型號、Android/API、RAM、螢幕更新率 | 掉幀、記憶體回收、圖片載入、返回鍵 |
| I | iPhone 實機（iOS 16.4 以上） | 機型、iOS、容量、更新率 | 手勢返回、音訊/觸覺、權限、背景恢復 |
| T | iPad 或 Android 平板實機 | 機型、OS、螢幕尺寸、方向 | 圖片裁切、格線、文字截斷、雙欄捲動 |
| W | 已部署的 Web/PWA（手機瀏覽器） | 瀏覽器版本、連線狀態 | 離線殼、更新、Web 音訊與儲存降級 |

每台裝置至少測一次「系統減少動態效果：開」及一次「App 低動態設定：開」。測試前關閉省電模式、背景下載與螢幕錄影以外的重負載 App；若刻意測低電量模式，需在結果中註明。

## 3. 固定測試資料與操作節奏

為了可比較，所有效能量測使用相同腳本：

1. 清除 App 資料或建立新的本機測試帳態；關閉雲端同步及 AI 網路請求，避免網路延遲混入結果。
2. 選擇「關聖帝君」，提問：`是否應先完成目前工作再規劃轉職？`，分類選「事業」。
3. 依序走完：選神 → 問事 → 上香 → 靜心 → 搖籤 → 三次連續聖筊驗籤 → 結果 → 加入筆記 → 回到首頁；另測一次驗籤失敗是否回籤筒重新抽籤。
4. 連續重複完整流程 5 次；第 1 次標記為冷快取，其餘為暖快取。
5. 另執行一次首頁瀏覽：神明選擇頁由頂到底捲動一次、回頂、點選最末一張卡、返回。

不要記錄真實個資、語音內容或私人求籤問題；提交螢幕錄影前要確認未包含通知、帳號或其他敏感資訊。

## 5. 效能量測方法

### 5.1 啟動、圖片與流程時間

以手機計時器或螢幕錄影逐次量測，單位為秒（保留一位小數）：

- **冷啟動可互動**：點擊 App 圖示至首頁第一個主要按鈕可點。
- **暖啟動可互動**：App 已在背景後切回前景至可操作。
- **首張神明圖**：進神明選擇頁至第一張卡圖片完整顯示。
- **選擇頁完成載入**：進頁至捲動和點選均可回應。
- **完整儀式**：從點擊「開始」到結果卡出現並可操作。

每個數值量 5 次，填入五次原始數據、平均值與最大值；不可只填「約」。冷啟動前須完全結束 App，暖啟動不可殺掉 App。

### 5.2 Android：畫面流暢度與記憶體

1. 在「開發人員選項」開啟 **Profile GPU Rendering / Profile HWUI rendering → On screen as bars**。
2. 依固定腳本錄製抽籤動畫與神明選擇捲動各 3 次；記錄最高柱狀圖、超過綠線的比例與是否看見明顯停頓。60 Hz 裝置以 16.67 ms 作為一個 frame 的參考線。
3. 若出現異常，以 Android Studio System Trace 或 Perfetto 擷取對應流程；在備註寫入 trace 檔名與發生時點。
4. 以 USB 偵錯連線時，在「首次完整流程後」與「連續 5 次後」各執行一次：

```powershell
adb shell dumpsys meminfo <application-id>
```

記錄 `TOTAL PSS`，不要混用不同 Android 版本的其他欄位。`<application-id>` 必須以實際建置輸出為準。

### 5.3 iOS：畫面流暢度與記憶體

1. 以 Xcode 連接實機，選擇候選 App 與裝置後執行 **Product → Profile**。
2. 用 **Core Animation** 觀察儀式與神明選擇捲動；用 **Time Profiler** 找主執行緒尖峰；用 **Allocations** 比較第 1 次與第 5 次完整流程後的常駐記憶體。
3. 將 `.trace` 檔依命名規則保存，並在表格填入平均 FPS（若工具提供）、可見掉幀、峰值/結束記憶體和觀察結論。

120 Hz 裝置不可拿 16.67 ms 當唯一門檻；要一併記錄螢幕更新率與 Instruments 顯示的 frame 結果。

### 5.4 可接受門檻（發布候選的建議 gate）

| 指標 | 建議門檻 | 阻擋發布的情況 |
| --- | --- | --- |
| 冷啟動可互動 | 低階 Android 5 次平均 ≤ 4.0 秒 | 任一次超過 8 秒、白畫面或當機 |
| 暖啟動可互動 | 5 次平均 ≤ 1.5 秒 | 無法恢復、狀態損毀或超過 4 秒 |
| 抽籤/捲動 frame | 60 Hz 裝置大多數 frame 低於 16.67 ms；不得有主觀可見連續卡頓 | 任一動畫 frozen frame（>700 ms）、無法結束或重複寫入紀錄 |
| 連續 5 次流程 | 不崩潰、不 ANR、不持續線性增加記憶體 | 當機、ANR、系統回收、或第 5 次相較第 1 次 PSS 增加超過 20% 且無法回落 |
| 圖片與觸控 | 全流程無空白肖像、嚴重裁切或失效操作 | 任一主要流程被阻斷 |

門檻是目前的發佈候選標準，不是跨所有硬體的理論 FPS 比較。任何沒有達標的測項都應建立 issue，附裝置資料、commit、重現率與量測證據。

## 7. 結案規則

要把「真機品質」標為完成，至少須有 A、I、T 三份回填紀錄，全部 F01–F13 已填、無阻擋 issue，且任一效能偏差都有已驗證的修正或經產品負責人明確核准的風險接受紀錄。Web/PWA 的 W 是發佈前必測，但不可取代三種原生裝置。
